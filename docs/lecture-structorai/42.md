### docs/db-reference/RLS-POLICIES-SUMMARY.md
- Récap généré des policies RLS de StructorAI (migrations 000 -> 044) : 54 tables, 144 policies ; usage = comparer à la vraie base (la vraie base avait 134 policies -> 10 MANQUANTES) ; l'annexe contient le DDL CREATE POLICY copiable dans Supabase ; après ajout : `NOTIFY pgrst, 'reload schema';` (recharger le cache PostgREST). Source : docs/db-reference/SCHEMA-REFERENCE.sql.
- Patron RLS (très réutilisable) : fonctions helper `public.org_id()` (organisation de l'utilisateur connecté), `public.is_admin()`, `public.is_super_admin()` ; tables métier = 4 policies (SELECT/INSERT/UPDATE/DELETE) rôle `authenticated`, nommées `<table>_<cmd>_own`, avec USING `organization_id = public.org_id()` ; SELECT et UPDATE ajoutent `AND deleted_at IS NULL` (suppression douce) ; INSERT = WITH CHECK `organization_id = public.org_id()` ; UPDATE a USING + WITH CHECK (empêche de déplacer une ligne vers une autre organisation). Tables de référence partagées (tva_rules, zones_btp, badges, quests...) = SELECT USING (true) pour authenticated. Tables « par utilisateur » (xp_events, user_badges, capsule_views, referral_codes) = `user_id = auth.uid()`.
- Tables à RLS activée SANS aucune policy = deny-all, accès uniquement par le backend (service_role) : `api_keys`, `stripe_events`. Pour `subscriptions` : une seule policy SELECT (own) -> l'écriture se fait uniquement côté backend via webhook Stripe. `organizations` : SELECT own (non supprimé) + UPDATE réservé à is_admin() . `ai_decisions` : journal inviolable (UPDATE et DELETE USING false), INSERT WITH CHECK (true), SELECT own. `testimonials` : policy SELECT pour le rôle `anon` sur `published = true AND revoked = false` (lecture publique d'un sous-ensemble) + gestion own pour authenticated. `avis_google` (table d'avis Google par organisation) : 4 policies own avec deleted_at. `photos_chantier` : 4 policies own avec deleted_at. `client_portal_tokens` : 4 policies own. `templates_devis` : SELECT `organization_id IS NULL OR = org_id()` (modèles globaux + propres).
- Points faibles visibles (déduction) : `ai_decisions_insert_system` et `churn_risk_scores_insert_system` ont WITH CHECK (true) pour le rôle authenticated -> n'importe quel utilisateur connecté pourrait insérer des lignes pour une autre organisation ; `users_insert_own`/UPDATE permettent à un utilisateur de modifier sa propre ligne (risque d'élévation si une colonne de rôle existe — à vérifier). Pas de policy pour les écritures sensibles = bien (deny par défaut).
- Réutilisable Sitô : COPIER ce patron : une colonne organization_id (ou artisan_id) sur chaque table, fonction helper org_id() lisant le profil de auth.uid(), 4 policies par table, WITH CHECK sur INSERT/UPDATE, deleted_at pour suppression douce, tables d'événements Stripe en deny-all (service_role seulement), abonnement en lecture seule pour le client, lecture publique `anon` limitée par un drapeau `published`. Penser au `NOTIFY pgrst, 'reload schema'` après création de policy/table. Comparer régulièrement la base réelle au fichier de référence (10 policies manquantes constatées sur 144).
