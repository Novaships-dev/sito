### supabase/_rebuild/apply-local.sh
- Monte le schéma complet sur la pile Supabase LOCALE (psql sur 127.0.0.1:54322), exclut les *_down.sql, tri par version (`sort -V`), 1 transaction par fichier, écrit un registre supabase_migrations.schema_migrations (clé = nom complet) et vérifie que le nombre enregistré = nombre de fichiers ; termine par `NOTIFY pgrst, 'reload schema'`. Variable : LOCAL_DB_URL (défaut postgres local). GARDE anti-prod : refuse toute cible hors 127.0.0.1/localhost:54322. Usage : `bash supabase/_rebuild/apply-local.sh`.
- Pourquoi (AUDIT-166, CHANTIER 7c) : la suite E2E tapait la Supabase de PRODUCTION -> 118 saturations du pooler (`EMAXCONNSESSION … pool_size: 15`) en un run, donc des 500 aléatoires et des specs rouges sans rapport avec le code, + 223 brouillons de terrain démo accumulés. Un projet Supabase dédié aux tests (~0 €) était IMPOSSIBLE : palier gratuit = 2 projets actifs max par organisation, déjà pris. Solution : pile locale.
- Pièges : (1) le CLI applique les *_down.sql et plante sur « 000 » dupliqué (mesuré le 06/08/2026) ; (2) deux paires de migrations partagent leur numéro (029_* x2, 030_* x2) -> avec version = préfixe, la 2e de chaque paire était appliquée mais non enregistrée (registre 114 vs 116 réels, corrigé le 07/08/2026) ; le même homonymie vaut pour la base distante où `supabase db push` compare par version (noté, non traité) ; (3) sans NOTIFY pgrst, PostgREST sert un cache de schéma périmé après ALTER TABLE (leçon AgentShield n°6). Au moment du script, ~116-117 migrations existaient (le dépôt a donc bien plus que les 43 de mon lot).
- Réutilisable Sitô : Supabase local + script de rejeu pour tests E2E sans toucher la prod ; garde anti-prod ; NOTIFY pgrst ; numéroter les migrations sans doublon.
